# AGENTS.md

Repository guidance for coding agents working on cocos-mcp-server. `CLAUDE.md`
imports this file and Codex reads it directly. Keep project facts here and
generic behaviour in the owner's global guidance; details live in the owning
documents linked below.

## Project

- A Cocos Creator editor extension (`package.json` `editor`: `>=3.8.6`) that exposes the editor over MCP so AI clients can drive scenes, nodes, components, prefabs, assets, preview, build and debugging. The MCP endpoint is `http://127.0.0.1:<port>/mcp` (default port 3000), next to REST routes (`/health`, `/api/...`) and the `/game/*` bridge used by the runtime client in `client/`.
- This repository is a fork of LiDaxian's `cocos-mcp-server` v1.4.0 (`package.json` `author`); the fork point is `754adec`, the last upstream commit in this history. Why the fork does not follow the upstream v1.5.0 plan: [ADR 0001](docs/adr/0001-skip-v1.5.0-spec.md).
- Several editor behaviours in [docs/landmines.md](docs/landmines.md) were observed on Cocos Creator 3.8.7; keep the version qualifier when citing them.
- `docs/` prose is Traditional Chinese for the maintainer. AI-facing files (`AGENTS.md`, `docs/landmines.md`) are English.

## Architecture

| Area | Path | Responsibility |
|---|---|---|
| Extension entry | `source/main.ts` | `load()` builds the tool registry, `ToolManager` and `MCPServer`; `unload()` stops the server and clears `require.cache` for this extension's modules so a reload picks up a rebuild. IPC methods are declared in `package.json` `contributions.messages`. |
| MCP server | `source/mcp-server-sdk.ts` | SDK low-level `Server` with `StreamableHTTPServerTransport`; `tools/*`, `resources/*`, `prompts/*`, REST short-circuit, `/game/*` bridge, loopback Host check. Server version is read from `package.json`. |
| Tool registry | `source/tools/registry.ts` | `createToolRegistry()` instantiates every category once; tools are exposed as `${category}_${name}`. |
| Tool categories | `source/tools/*-tools.ts` | One `ToolExecutor` class per category; tools declared with `@mcpTool` (`source/lib/decorators.ts`); long descriptions for some categories in `source/data/*-docs.ts`; a description without a `[primary]` / `[compat]` / `[specialist]` prefix is listed as `[specialist]`. |
| Tool enable state | `source/tools/tool-manager.ts` | Named configurations of enabled tools, persisted in `<project>/settings/tool-manager.json`; `MCPServer.updateEnabledTools()` filters `tools/list`, and an empty set lists every tool. |
| Resources | `source/resources/registry.ts` | `cocos://` resources: tool-backed ones call read-only tools; docs ones read files under `docs/` at request time (`cocos://docs/landmines` serves `docs/landmines.md`). |
| Prompts | `source/prompts/registry.ts` | Prompt templates with project context baked in. |
| Notifications | `source/lib/broadcast-bridge.ts` | Editor broadcasts → debounced `notifications/resources/updated`. |
| Asset interpreters | `source/asset-interpreters/` | Importer type → interpreter map behind the `assetMeta` tools; unknown importers fall back to a read-only interpreter. |
| Scene bridge | `source/lib/scene-bridge.ts` → `source/scene.ts` | `runSceneMethod` wraps `execute-scene-script`; `source/scene.ts` runs in the scene process. |
| Settings and flags | `source/settings.ts`, `source/lib/runtime-flags.ts` | `<project>/settings/mcp-server.json`; runtime flags for editor-context eval and scene log capture. |
| Panel | `source/panels/default/`, `static/` | `Editor.Panel.define`: a Vue 3 app mounted in `ready()` and unmounted in `close()`; composables for server status, settings and tool configuration; template and style under `static/`. |
| Shared helpers | `source/lib/` | zod → JSON Schema (`schema.ts`), logger (`log.ts`, debug output gated by `enableDebugLog`), response, dump and lookup helpers, CORS. |

Tool inventory: [docs/tools.md](docs/tools.md) is the authoritative listing once regenerated. To measure the source, run `npm run build` (rewrites tracked `dist/`), then the registry count command in [HANDOFF §環境快速確認](docs/HANDOFF.md), then `node scripts/generate-tools-doc.js`. Do not copy counts or a version history into this file.

## Commands

There is no test runner and no CI. `smoke`, `check:gemini` and the doc generator read `dist/`, so build first. Use project-local tooling (`npx` resolves the local TypeScript).

| Check | Command | Notes |
|---|---|---|
| Install | `npm install` | Runs `scripts/preinstall.js` (environment and `@cocos/creator-types` check) |
| Types | `npx tsc --noEmit` | Writes nothing |
| Build | `npm run build` | `tsc` → `dist/`, then `scripts/gen-build-hash.js` writes `dist/build-hash.json`; rewrites tracked files |
| Watch | `npm run watch` | `tsc -w` into `dist/` |
| SDK smoke | `npm run smoke` | Stub registry; no editor needed |
| Gemini schema guard | `npm run check:gemini` | Fails on `$ref` / `$defs` / `definitions` ([landmine 15](docs/landmines.md#landmine-15)) |
| Tool reference | `node scripts/generate-tools-doc.js` | Overwrites `docs/tools.md` |
| Token measurement | `node scripts/measure-tool-tokens.js` | `tools/list` payload size against router simulations |
| Patch whitespace | `git diff --check` | |

Not routine: `node scripts/live-test.js [--port 3000]` needs a running editor with the extension started on a suitable project. It creates, mutates and deletes nodes, scene assets and prefab assets and switches scenes; it restores state in `finally` blocks but can still leave changes and trip modal dialogs ([landmine 14](docs/landmines.md#landmine-14)). Run it only on the owner's instruction, against a throwaway project. `scripts/probe-broadcast.js` likewise needs a running editor with editor-context eval enabled ([landmine 13](docs/landmines.md#landmine-13)).

Static checks do not exercise the editor. Behaviour inside Cocos Creator is accepted only after the extension is reloaded and exercised in the editor; report static results as static, never as editor verification.

## Conventions

- TypeScript strict; `npx tsc --noEmit` passes before a commit.
- Three runtime contexts. Scene-side code (runs in the scene process through `execute-scene-script`) belongs in `source/scene.ts`; add a new scene method both to its `methods` and to `package.json` `contributions.scene.methods`. Editor-host code (Node.js main process) belongs in `source/main.ts`, `source/tools/` and `source/lib/`. Panel code (`source/panels/`) runs in the panel's browser context and reaches host state through `Editor.Message.request` to the methods in `package.json` `contributions.messages`.
- Each category class implements `ToolExecutor`: `getTools()` returns the definitions and `execute()` dispatches by name. Both come from `defineToolsFromDecorators(this)` over `@mcpTool` methods, so a new tool is one decorated method with a zod `inputSchema`, not a hand-written switch branch. Registry keys stay free of `_`: the server splits an exposed name at its first `_`.
- When unsure about an `Editor.Message` channel, check `@cocos/creator-types` instead of adding try-catch fallback ladders.
- `dist/` is `tsc` output, tracked because the extension ships without a build step. Never edit it by hand; rebuild and commit it with the source change.
- `version`: bump `package.json` (and `package-lock.json`) after any change under `source/` — patch for fixes, cleanup, refactors or a single backlog item; minor for new MCP tools or a wider public surface; major only when asked. Documentation-only changes need no bump. A coordinated batch of code commits gets one bump at the end. The editor shows this version in its panel and the server reports it to MCP clients, so a stale version hides whether a reload picked up the change.
- `releaseDate`: ISO 8601 datetime with the `+08:00` offset (`"YYYY-MM-DDThh:mm:ss+08:00"`), bumped together with `version`. The editor does not validate it; a date-only value loses ordering when several bumps land on one day.
- Install and reload: the extension folder is `<project>/extensions/cocos-mcp-server/`. Linked (symlink on macOS/Linux, junction on Windows) means `dist/` is already live and only a reload is needed (restart the editor or reload extensions). Copied means copying `dist/` and `package.json` to the install path after each bump, then reloading. The three docs resources read `docs/landmines.md`, `docs/tools.md` and `docs/HANDOFF.md` under the extension root; a copy without those files serves the tools normally and answers those resources with "Resource unavailable", so copy them too when the resources are needed. The per-machine path and link type are recorded in [HANDOFF §環境快速確認](docs/HANDOFF.md) for one machine; confirm on the current machine and do not hard-code paths elsewhere.

## Review workflow

Scope, review dimensions and authorisation follow the owner's global review rules (Claude: `~/.claude/rules/review-defaults.md`; Codex: `~/.codex/AGENTS.md`). This section adds the project sequence and triggers.

1. Implement locally and run the matching checks.
2. Run an independent, read-only review of the uncommitted working tree.
3. Adjudicate the findings and fix the accepted ones.
4. Re-review: every original finding is addressed and no new defect appears.
5. Commit and push only on the owner's instruction. Choose the commit split and version bump after the review settles, not one patch bump per review loop.

A three-way review applies when a change adds an MCP tool, resource or capability; refactors ≥5 tool files or ≥200 LOC of `source/`; adds a host-side eval, filesystem-write or IPC path; or needs a minor bump. Skip it for typos, single-line bugs, comment edits and documentation-only changes.

- Reviewers run in parallel with independent context: a Claude reviewer subagent; Codex through `codex exec -s read-only "<review prompt>" < /dev/null` with a review-capable prompt; `gemini` with the diff on stdin and the prompt as `-p`. A rescue or task-delegation agent never acts as a reviewer.
- Every reviewer receives the full agreed scope (the diff plus the whole touched files), the relevant callers and dependents, the focus (security, correctness, regressions, edge cases), and explicit instructions not to edit, commit or push. Findings carry P1 / P2 / P3 with `file:line` and a concrete fix.
- A missing or failing reviewer tool is reported as not run; it never counts as a completed review.
- Every P1 is fixed or rebutted with evidence. A P2 raised by two reviewers is fixed only within the agreed scope; agreement is not authorisation for a new design or a wider scope, which goes to the owner.
- Disputed findings stay visible in the report with each side's reasoning. Record the consolidated findings, who raised them and the disputed items in `docs/HANDOFF.md`.
